# ITEM_2.LDT 二进制格式解析笔记

## 文件概况
- 大小: ~5,392,563 字节
- 列数: 125
- 行数: 9582

## LDT头部结构（与标准LDT不同！）

```
偏移  大小  内容
0     4     unk (值为0)
4     4     列数 (125)
8     4     行数 (9582)
12    列数×64  列名字段 (每个字段64字节，\x00结尾+空格填充)
```

## 类型区（反直觉！）

**列名区之后**是类型区（125列 × 4字节 = 500字节）。

**关键特点**：类型区中**所有125列的类型值都是0**（即标记为string类型）。但这与实际存储不符！数据区的第0~47列实际以4字节int存储，不是string。

## 数据区

数据区从 `12 + 列数×64 + 列数×4` = 8512 开始。

**数据行结构**：
- 前48列（索引0~47）每列4字节（int32），即使它们的类型标记为0(string)
- 第48列及以后按类型区的实际类型值解释
- 实际行大小 = 48×4 + sum(types[48:])

```
行0数据：
000: 03000000 03000000 03000000 03000000   ← _Category[0], _Num[1], _ColorID[2], _Name[3] 都是int
010: 03000000 03000000 03000000 03000000   ← col4~7
020: 03000000 03000000 03000000 03000000
030: 02000000 01000000 03000000 03000000
...
0c0: 00000000 00000000                      ← 行尾
```

## 关键列索引（前48个int列）

| 索引 | 字段名 | 说明 |
|------|--------|------|
| 0 | _Category | 物品分类（种类繁多，非标准映射） |
| 1 | _Num | **物品ID（等同于ItemID）** |
| 2 | _ColorID | 颜色ID |
| 3 | _Name | 名称（int，不是string！需要查GLString表） |
| 4 | _Description | 描述（int，GLString引用） |
| 5 | _Use_Type | 使用类型（位掩码，65536/16777216/256等） |
| 6 | _Icon | 图标文件ID |
| 7 | _IconIndex | 图标索引 |
| 10 | _CashCheck | 0=禁止商城, 1=允许 |
| 13 | _Type | 物品大类 |
| 14 | _SubType | 物品子类 |
| 15 | _PosID1 | 装备位置 |

## _Name字段存储形态

_NAME(索引3)的值是int32，不是string！其含义有3种：
1. **0** = 无名（空道具）
2. **3** = 实际中文名称（？）
3. **其他数值** = GLString表的引用ID

这意味对_NAME=0或=3的道具，名称字符串存储在别的位置（可能在LDT文件末尾的字符串池，或在SPF包的GLOBAL_STRING.LDT中）。

## 与CASH_SHOP.LDT的区别

| 特性 | CASH_SHOP.LDT | ITEM_2.LDT |
|------|--------------|------------|
| 实际存储 | 定宽记录（各列类型明确） | 前48列固定4B int，后续按类型表 |
| _ItemID列 | 有（_ItemID1~8） | 无，用_Num代替 |
| _Name | string（直接存中文） | int（GLString引用或0/3） |
| 行数 | 1704行 | 9582行 |
| 二进制编辑 | 可以（但需注意string长度） | **非常困难，不推荐代码解析** |

## 实操建议

- **ITEM_2.LDT**：用彩虹岛编辑器（D:\LaTale\小九三合一\）查看和编辑，不要尝试用Python/脚本直接解析
- **二进制搜索**：可以在ITEM_2.LDT中搜索特定ItemID的4字节小端字节（如1200000002 = 0x47868C00），找到后手动偏移到_Name列读GLString引用
- **跨端对比**：两个端的ITEM_2.LDT如果大小相同，大概率只是文本差异（繁简转换等），可以用二进制diff验证
