# Pack=0 目录模式验证（2026-05-26）

## 背景

尝试在旧版他乡exe上通过 Pack=0 目录模式绕过SPF加密问题。直接原因是用户需要修改LDT文本来实现简中化，但SPF打包工具（SFP v1.6）的打包功能被作者禁用（灰色不可点击）。

## 测试配置

- 服务端: D:\\Server\\BIN2\\ 全套 7 个旧版他乡exe
- LDT目录: D:\\Server\\SPF\\ROWID\\DATA\\LDT\\（SFP v1.6解包出来的LDT，仅ROWID.SPF的内容）
- 配置修改: configure.ini 中所有10处 pack=1 → pack=0，备份为 .bak3

## 测试结果

| 服务 | pack=0 结果 | pack=1 结果（对照） |
|------|------------|-------------------|
| MgmtServer | ❌ 进程存活但不绑端口 | ✅ 正常绑10001 |
| AS | ❌ 进程存活但不绑端口 | ✅ 正常绑10020 |
| LoginServer(编译版) | ✅ 正常绑19999 | ✅ 正常绑19999 |
| LobbyServer | ❌ 进程存活但不绑端口 | ✅ 正常绑10002 |
| BayServer | ❌ 进程存活但不绑端口 | ✅ 正常绑10006 |
| RoomServer | ❌ 进程存活但不绑端口 | ✅ 正常绑10007 |
| GameServer | ❌ 进程存活但不绑端口 | ✅ 正常绑20001 |

**进程全在但端口全没绑** → 所有旧版exe都在初始化阶段卡住了。

## 日志错误

所有服务端 console 输出相同的错误序列：
```
GLOBAL_SYS.LDT : FAILED !  (This LDT is Not Exist.)
```

还有其他LDT文件也报找不到。GLOBAL_SYS.LDT 是服务端专用的游戏系统参数表，被他乡作者从SPF中删除了（B站说明第4条"超级加密删除无需客户端读取的LDT"）。

## 根因分析（2026-05-26 最新理解）

### 表层原因
他乡SPF做了"超级加密"——删除了服务专用LDT文件（GLOBAL_SYS.LDT等）。SFP v1.6解包出来的LDT目录缺这些文件，所以pack=0读目录时找不到。

### 深层原因（关键）
`GLOBAL_SYS.LDT : FAILED !` 错误消息不只是"文件不存在"的报告。旧版他乡exe有**内建的SPF校验/防篡改机制**：

1. exe启动时读SPF文件列表（在SPF尾部目录中）
2. 如果列表中找不到某些关键LDT（如GLOBAL_SYS.LDT），exe认为文件损坏/被篡改
3. 触发保护逻辑：断开后续初始化，不绑定端口，进程存在但不工作

**为什么会保护而非优雅降级**：他乡作者卖服务端给私服站长，他的SPF加密 + exe魔改保证了：如果站长换了SPF/LDT，服务端就启动不了。这是吃这碗饭的护城河。

## 验证结论

| 假设 | 验证结果 |
|------|---------|
| 把全部SPF都解包把所有LDT补全就能跑 | ❌ 大概率也不行 — exe可能在启动时比对SPF目录CRC |
| 编译版在pack=0下行不行 | ✅ 可以 — 编译版exe没有保护逻辑 |
| 旧版他乡exe在pack=0下不行 | ✅ 确定 — 保护机制触发 |
| 是否可以通过patch exe跳过保护 | 🔍 可能 — 但exe可能被VMProtect加壳，patch不可行 |

**最终建议**：旧版他乡exe只能用pack=1模式读SPF包。想改文本必须通过SPF打包工具重新打包，或换用编译版。
