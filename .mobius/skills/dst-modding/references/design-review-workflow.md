# 设计评审类任务的工作流（用户偏好）

适用：用户说「你先设计」「这个怎么做」「我想做个 X」但**不要代码**时；以及他在几个方案之间摇摆时。

## 1.「你先设计」= 只出设计稿，不写代码
- 写进 **mod 目录**的 md（项目惯例：`musha-backlog.md` 记进度与决策，`<主题>-design.md` / `*-plan.md` 放设计正文）。
  本例产出：`mods/musha/musha-panel-tabs-and-settings-design.md`（v1→v2→v3 逐轮回写）。
- 稿子结构（照这个排）：
  目标 → 现有代码基线 → 数据结构/API → UI 结构（画成目录树） → 关键交互 → 分期表（P1..Pn + 依赖） → 给美术的清单 → **已定 / 待确认**。
- ★**「已定」与「待确认」必须分成两段**。待确认项给**字母选项**（A/B/C/D + 「D 别的意思，说一句」），他回一个字母就够。
- **他口语里提的修改，当场回写进设计稿**。他说"记一下""暂时记录等会看"就真去记（写进稿子或 backlog 的待定条目），否则下一轮必然重问。
- 稿子写完就停手——"先设计"= 别顺手写代码。

## 2. 设计稿要能"防反复"
- 一旦拍板，在稿子里写成 **「🔒 已拍板·防反复」** 段落并附理由。他后面动摇时翻这一条即可。
- 拍板优先选**低成本可逆**的路：先骨架、先复用现成模块、大而美单开一期。

## 3. 他摇摆时替他拍板（明确偏好，别陪着纠结）
原话样本：**"技能页大了是很好看 但很折腾" / "大脑在疯狂的跟自己打架" / "又不确定对不对"**。
- 别列"各有优劣"、别问他想怎么样。**直接给结论 + 理由 + 具体切法。**
- 标准切法：**先做能用的小版本（骨架），把"好不好看/要不要做大"推迟到他在游戏里见过实物之后判断。**
- 他吃得下的论证：*"你现在是拿想象对比大而美，没有实物参照，当然越比越乱；骨架跑通、进游戏能看见能摸，判断才有依据。"*
- 顺手把"真正新写的只有 N 样"逐条列出来，把恐惧拆小（本例：五页框架 + 导航 + 设置组件 + 设置页，其余页全是搬运/占位）。
- 拆"折腾"的根因：大而美要同时动 **美术素材 + 布局 + 交互** 三样；小版本只动"搬位置"。

## 4. 什么时候该问、什么时候不该问（最容易搞反的一条）
| 类型 | 做法 |
|---|---|
| UI 数值 / 配色 / 像素位移 / 某个子句归哪个元素 | **别问，直接按最合理理解改**。回话写明"我改的是 X"，留一句"不对说一声"。发 clarify 会被取消 → 白花一轮。 |
| 设计方向 / 结构 / 页数 / 权限归属 / 数据源 | **必须列"待确认"让他拍板**（字母选项）。擅自决定会返工。 |

## 5. 收尾习惯
- 回话结构：**结论先行**（能 / 不能 / 分情况）→ 原因（引用具体 `文件:行`）→ 一条可执行的下一步（例："要不要我先做个样例把这条路走通"）。他认可这种收尾。
- 大活开工前提醒**"存档 + 开新会话"**（他在意 token 消耗），并估一句这活比 UI 微调大多少量级。

## 6. 零碎但会重复踩的
- ★**"11" / "111" / "1" 这类裸数字 = 催活暗号**（"提醒工作啦"）。当 nudge 处理，直接接着干，
  **别反问"1 是什么意思"**（问了他也不解释，只浪费时间）。回话里可以带一句"那个 1 我当你催活"。
- ★**"你去找找 X"（找参考图/参考色）别委派子代理**：用过一次 web 子代理，600s 超时白等。
  本地 `curl` + 十几行 Python 直接干（通道与取色脚本见 `references/screen-scrolling-grid.md` 的
  「找参考色 / 参考图」节）。**空手回来是硬伤** —— 找不到就给 2–3 个候选色号收尾。
- ★**设计稿是 SSOT，但"待定项"要能在下一轮被找回来**：他说"暂时记录，等会看"就写成
  `- [ ] ⏸【待定·用户暂缓】…`（含代码位置），别只口头应下。
- ★**大活收尾要把"风险点/待验证"自己标出来**，不要写"已完成，请测试"。
  格式：`⚠️ 待进游戏验证 / 风险点` 列表，每条附备选方案。他自己能一眼给方向。
